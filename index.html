Week 1 · D1–D7

1주차 — 기반 구축

01
기반 구축 주간
DB 스키마 · FastAPI · STT/TTS 파이프라인 · 초기 프롬프트 · 온보딩 UI
주말 목표 음성 → LLM → 음성 기본 루프 동작
일자역할작업우선도완료 기준 (Definition of Done)
D1 (월) ③ DB 스키마 전체 확정
  • users, sessions, diagnosis_history, voice_files, guardians, experts 테이블
 MUST ERD 문서 공유, 전원 리뷰 완료
D1 (월) ② STT/TTS 엔진 선택 결정
  • Whisper API vs Clova Speech 비교 후 채택
  • TTS: Clova Voice 또는 Azure TTS
 MUST 선택 이유 슬랙 공유 + 계정 발급
D1–D2 ① 노인 특화 AI 페르소나 정의
  • 이름·말투·주제 제한 범위 문서화
  • 위기 상황 금지 표현 목록
 MUST 페르소나 프롬프트 v1 문서 완성
D1–D3 ② FastAPI 서버 + WebSocket 엔드포인트
  • /ws/voice — 스피커 실시간 연결
  • /api/session — 세션 CRUD
 MUST WebSocket ping/pong 테스트 통과
D1–D4 ② STT → LLM → TTS 파이프라인
  • 음성 수신 → 텍스트 변환 → Claude API → TTS 응답
  • 평균 레이턴시 목표: 3초 이하
 MUST "안녕하세요" 말하면 AI가 음성으로 답 가능
D2–D3 ③ PostgreSQL × 2 구성 + 마이그레이션
  • 일반 DB (프로필·세션), 민감 DB (음성·진단)
 MUST Alembic 마이그레이션 성공
D3–D5 ③ OTP/PIN 인증 구현
  • 전화번호 → coolSMS OTP 발송 → 검증
  • 세션 토큰 만료 72시간 설정
 MUST 테스트 번호로 OTP 수신·로그인 성공
D3–D6 ④ React + TypeScript 프로젝트 셋업
  • 온보딩 UI (큰 글씨·선택지 기반)
  • PHQ-9 설문 UI (7문항 선택지)
  • STT 실패 시 텍스트 폴백 UI
 HIGH 설문 완료 → 점수 화면 렌더링
D4–D6 ① PHQ-9 매핑 + 프롬프트 라우팅
  • 점수 구간별 시스템 프롬프트 분기
  • 국립정신건강센터 자료 기반 문항 검증
 MUST 점수 0~27 → 4개 구간 프롬프트 분기 동작
D4–D6 ② Claude API 연동 + 세션 흐름 테스트
  • 프롬프트 주입 → 응답 → 저장 루프
 MUST 5회 연속 대화 유지 테스트 통과
D7 (일) 전원 1주차 통합 데모 + 회고
  • "말하면 AI가 답하는" 기본 루프 시연
  • 블로커 정리 → 2주차 계획 조정
 MUST 스피커 → AI 대화 1회 성공 시연
1주차 성공 지표: D7 금요일에 스피커에 말하면 AI가 맥락 있게 음성으로 답하는 기본 루프가 동작해야 합니다. 이게 안 되면 2주차 전체 계획이 붕괴됩니다.
Week 2 · D8–D14

2주차 — 핵심 기능 구현

02
핵심 기능 주간
진단 에이전트 · 위기 감지 · 음성 분석 · 알림 시스템 · 사용자 포털 UI
주말 목표 위기 감지 → 보호자 알림 동작
일자역할작업우선도완료 기준
D8–D10 ① 진단 에이전트 순환 구조
  • 대화 요약 → 점수 업데이트 → 프롬프트 재조정 루프
  • diagnosis_history 테이블에 delta 저장
 MUST 3회 대화 후 진단 점수가 업데이트됨 확인
D8–D9 ② 세션 관리 고도화 + 무활동 감지
  • 20분 무활동 → "아직 계세요?" 음성 알림
  • 30분 후 자동 세션 종료 + 요약 저장
 MUST 무활동 타이머 테스트 통과
D8–D10 ③ 음성 원본 스토리지 구축
  • S3 또는 MinIO 연동
  • AES-256 암호화 저장
  • 접근 감사 로그 테이블
 HIGH 음성 파일 업로드·복호화 테스트 통과
D8–D14 ④ 사용자 포털 UI 완성
  • 감정 추이 차트 (주간·월간)
  • 대화 이력 뷰어
  • 스피커 연결 상태 표시
  • 설정 페이지 (보호자 등록)
 HIGH 사용자 로그인 → 대시보드 전체 렌더링
D9–D11 ② 음성 비언어 분석 (librosa / pyAudioAnalysis)
  • 음높이(pitch) · 속도(tempo) · 에너지 추출
  • 분석 결과를 진단 에이전트에 피처로 투입
 HIGH 분석값이 diagnosis_history에 저장됨
D10–D12 ① 위기 감지 2단계 로직
  • 위험 단어 사전 + 문맥 score 계산 (0~1)
  • score < 0.4: 확인 질문 / 0.4~0.7: 앱 알림+상담번호 / 0.7~0.9: 보호자 확인 요청 / >0.9: 즉시 119
 MUST 테스트 스크립트 5종 → 정확한 분기 확인
D11–D13 ② 알림 API (SMS · 이메일 · FCM)
  • coolSMS 연동 SMS 발송
  • 보호자 앱 FCM 푸시 (선택)
  • 위기 알림 템플릿 (상황별 3종)
 MUST 실제 전화번호로 위기 알림 SMS 수신 확인
D11–D13 ③ RBAC 권한 테이블 + 3포털 분리
  • user / guardian / expert 역할별 API 접근 제한
  • JWT claim에 role 포함
 HIGH 보호자 토큰으로 사용자 대화 직접 접근 불가 확인
D14 (토) 전원 2주차 통합 데모 + 회고
  • 위기 대화 시나리오 → SMS 알림 수신 데모
  • 3주차 포털 작업 우선순위 확정
 MUST 위기 감지 → 보호자 SMS 수신 성공
2주차 성공 지표: 위기 단어가 포함된 대화 시 2단계 로직이 작동하고, 실제 전화번호로 SMS 알림이 도착해야 합니다. 이게 없으면 서비스를 공개할 수 없습니다.
Week 3 · D15–D21

3주차 — 포털 완성 & 배포

03
포털 완성 & 배포 주간
보호자 포털 · 전문가 포털 · Function Calling · HTTPS 배포 · 지자체 데모
D21 목표 지자체 관계자 대상 데모 시연
일자역할작업우선도완료 기준
D15–D17 ④ 보호자 포털 UI
  • 주간 감정 리포트 (차트 + 요약)
  • 위기 알림 내역 (일시·심각도·조치 이력)
  • 안부 미확인 현황 (비접속 경보)
 MUST 보호자 계정 로그인 → 리포트 전체 렌더링
D15–D16 ①
②		 Function Calling 구현
  • call_guardian(message) — 보호자 즉시 연락
  • call_119(location, situation) — 응급 신고
  • refer_counselor(type) — 전문 상담 연계
 MUST score > 0.9 시나리오에서 119 함수 호출 확인
D15–D16 ③ 비접속 감지 Celery Beat
  • 매일 오전 9시 마지막 접속 24시간 초과 사용자 체크
  • 48시간 → 보호자 문자 / 72시간 → 공무원 알림
 MUST 테스트 계정 72시간 미접속 후 알림 발송 확인
D15–D17 ② 3포털 통합 API 완성
  • GET /guardian/report/{user_id}
  • GET /expert/high-risk-users
  • POST /expert/intervention-log
 MUST Postman 컬렉션 전체 통과
D16–D18 ④
① 지원		 전문가 / 지자체 포털 UI
  • 고위험군 목록 (위험도 배지 · 최근 대화 요약)
  • 개입 기록 작성 폼
  • 지자체 보고서 다운로드 (PDF)
 MUST 전문가 계정 → 고위험군 목록 렌더링
D17–D18 전원 전체 통합 테스트 (시나리오 기반)
  • 정상 대화 시나리오 3종
  • 위기 대화 시나리오 (경증·중증·응급) 3종
  • 보호자 수신 확인 · 전문가 포털 확인
 MUST 6개 시나리오 전부 예상 결과와 일치
D18–D19 ③ HTTPS 배포 + 보안 점검
  • SSL 인증서 적용 (Let's Encrypt)
  • API 키 환경변수 분리 확인
  • 개인정보처리방침 페이지 배포
 MUST 외부 URL로 전체 기능 접근 가능
D19–D20 전원 버그 픽스 + 데모 시나리오 준비
  • 5분 데모 시나리오 스크립트 작성
  • 지자체 관계자용 가이드 문서 작성
 HIGH 데모 리허설 1회 완료
D21 (일) 전원 최종 배포 확인 + 회고
  • 프로덕션 환경 최종 점검
  • 3주 회고 (KPT 방식)
  • 다음 스프린트 백로그 작성
 HIGH 지자체 데모 시연 가능 상태 확인
3주차 성공 지표: D21에 외부인(지자체 관계자 또는 보호자 역할 테스터)이 데모를 보고 "실제로 쓸 수 있겠다"는 피드백을 받으면 성공. 보호자 포털에서 주간 리포트를 확인하고, 전문가 포털에서 고위험군 목록이 보이면 충분합니다.

리스크 & 대응 방안

STT 레이턴시 초과
Whisper API가 느린 경우 대화 흐름이 끊김. 목표 3초 이하. 3초 초과 시 노인이 답하는 걸 포기함.
대응: D4까지 레이턴시 측정 후 기준 초과 시 Clova Speech(국내 서버)로 즉시 전환. 로컬 Whisper.cpp 폴백 준비.
④ 프론트엔드 3주차 과부하
보호자 포털 + 전문가 포털이 D15~D18에 집중. 1명이 3일 안에 2개 포털을 완성해야 함.
대응: ① 역할이 D15부터 전문가 포털 UI 지원. 전문가 포털은 MVP 범위를 고위험군 목록 + 개입 기록 2개로 제한.
위기 감지 오탐
"죽도록 맛있다" 같은 일상 표현이 위기 신호로 오탐될 경우 신뢰 문제 발생. 허위 119 신고 시 법적 문제.
대응: 단어 단독 감지 금지. 문맥 + 최근 진단 score 조합 필수. 0.9 이상만 119. 테스트 케이스 10종 이상 통과해야 배포.
DB 스키마 후반 변경
D1에 스키마를 확정하지 않으면 이후 모든 API에 영향. 중간 변경 시 전체 일정 3~5일 지연.
대응: D1 오전에 4인 전원 스키마 리뷰 1시간 의무 진행. 이후 변경은 마이그레이션 파일 추가만 허용, 기존 컬럼명 변경 금지.
Claude API 비용 급증
노인 사용자의 경우 대화 시간이 길어 토큰 사용량이 예상보다 클 수 있음. 개발 중 테스트 비용도 발생.
대응: 개발 환경은 claude-haiku 사용. 프롬프트 캐싱 적용. 세션당 최대 토큰 상한 설정. 일별 API 비용 모니터링 알림 설정.
3주 안에 WebSocket 불안정
음성 스트리밍 WebSocket 연결이 끊기거나 지연될 경우 대화 품질 저하. 특히 스피커 재연결 처리가 복잡.
대응: D3까지 ping/pong 재연결 로직 구현. 연결 실패 시 3회 자동 재시도. 재시도 실패 시 "잠시 후 다시 말씀해주세요" 안내.
절대 지켜야 할 규칙: 위기 감지 로직이 완성되지 않은 상태로 실제 사용자에게 배포하면 안 됩니다. 오탐으로 인한 허위 신고 또는 미탐으로 인한 방치 모두 법적·윤리적 문제가 됩니다. D12까지 2단계 로직이 완성되지 않으면 배포 일정을 연기해야 합니다.
